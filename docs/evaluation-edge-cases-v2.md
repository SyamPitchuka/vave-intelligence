# Evaluation results: edge-case set v2

Measured on 28 October 2026 against the hosted Neon development database, with the live stored settings: offline mode, MiniLM embeddings, Ollama not reachable (so every verdict is the heuristic one), `semantic_duplicate_threshold` 0.82, `fuzzy_strong_threshold` 86, `retrieval_top_k` 15.

> **Re-baselined 28 October 2026 on deterministic embeddings. These figures supersede every earlier run, including the earlier versions of this page.** Before the fix, `idea_embedding_text` listed an idea's vehicles in database row order. That order varies between loads, so the same idea could get a different vector after a reload or a re-index. Cosine moved by up to 0.011 between runs of unchanged code. The list is now sorted, every idea was re-indexed (re-index job `ebac15fb`, 117 of 145 idea vectors changed), and every run below uses the new vectors.
>
> **Reproducibility check:** each set was run twice after the re-index, and every cosine was compared as an exact float with no tolerance:
>
> | Set | Cosine values compared | Values that differed |
> | --- | --- | --- |
> | v2 hard set | 1,188 | 0 |
> | Edge v1 | 36 | 0 |
> | Edge v2 | 44 | 0 |
>
> Verdicts, ranks and unlabelled flags were also identical between the two runs. Stages that a setting can't switch were reproduced with measurement-only wrappers that override the runtime config for one run, with no code change: the symmetric score on, the semantic route off, and the low-voltage list emptied.

- **Workbook:** `data/vave_duplicate_edge_cases_v2.xlsx`, generated by `scripts/edge_cases_v2.py`.
- **Contents:** 14 historical ideas (VAVE-FH-001 to -014), 22 queries (VAVE-FQ-001 to -022) and 22 labelled pairs: 16 negatives and 6 positives.
- **Lexical properties:** `scripts/measure_v2.py` prints them.

**This set is a different instrument from [set v1](evaluation-edge-cases.md).** Set v1 was written without sight of the classifier, and every case in it was something the system got wrong. Set v2 was written knowing which rules exist. It probes their weak directions and gives each probe type a positive and a negative case, so a rule that fires too readily loses marks. That makes it a stronger test of over-firing and a weaker test of generalisation. It does not replace a held-out set written blind.

This is the last classifier change in this series. The remaining failures are documented under [Further work](#further-work) and have not been fixed.

## Summary

- **The lexical duplicate rule now requires a matching component** (`lexical_requires_component`). Near-identical text about a different or differently qualified component is now Similar but Distinct rather than Potential Duplicate. It is still shown, because a near-identical change to an adjacent part is useful to an engineer.
- **That rule fixed 5 edge v2 negatives** (FQ-002 to FQ-006), and every positive still passes.
- **v2 hard set:** precision **0.935**, recall **0.800**, F1 **0.862**, mean rank 1.200, rank@1 0.833. The component rule changed no verdict there, and no duplicate was lost: all 90 v2 duplicate pairs have matching component names.
- **Edge set v1:** the component rule changed no verdict, and every Tier 1 and Tier 2 gain holds.
- **Edge v2 passes 10 of 16 negatives, and 7 of those are real detections.** The other 3 pass only because cosine fell under 0.82 ([accidental passes](#accidental-passes-and-the-threshold)).
- **The determinism fix moved one edge v2 verdict.** FQ-016, a different_programme negative, went from 0.817 to 0.836, so it is no longer an accidental pass but a failure.
- **13 labelled v2 verdicts sit within 0.01 of the 0.82 cosine threshold,** and each is decided by that threshold alone.
- **Of the 18 near-threshold verdicts cited before the fix, 6 changed side** ([table](#accidental-passes-and-the-threshold)).
- **The component subset guard fixed nothing on any current set** ([note](#component-matching-a-wrong-premise-and-a-guard-that-fixed-nothing)).
- **The symmetric fuzzy score is off.** Turning it off changes no labelled pair on any set.
- **No rule or threshold was changed for the re-baseline.**

## Changes on 28 October

| Setting | Default | Change |
| --- | --- | --- |
| `lexical_requires_component` | on | **The lexical route ignored the component, so this was a routing defect, not a threshold one.** The rule (fuzzy ≥ 86, or Jaccard ≥ 0.62, or same action with Jaccard ≥ 0.42 and fuzzy ≥ 68) returned Potential Duplicate before component identity was ever checked. It now uses the existing component matcher, `components_match`, the same one the semantic route uses: fuzzy matching, abbreviation expansion and the subset guard. If the text matches but the components don't, the verdict is **Similar but Distinct**, with the explanation that the descriptions overlap but concern different components. A pair with no component on either side is not judged by this rule, so `scripts/evaluate.py`, which passes no query component, is unaffected. An exact description match still returns Potential Duplicate whatever the component. |
| `component_subset_guard` | on | The two component names are a different component in two cases. First, one name contains the other plus extra words, and those words include something other than assembly, part, component, unit or complete. Second, either name has a positional or ordinal qualifier the other lacks: front, rear, upper, lower, left, right, LH, RH, inner, outer, first or second. |
| `symmetric_lexical_fuzzy` | **off** (was on) | It changes no labelled verdict on any set. It also makes the system safe only while the semantic route is on, which ties two settings together. **The finding still stands:** `token_set_ratio` is containment-friendly. A query that contains the candidate's text plus more scores 90 or above (v1 superset queries 90.2 and 90.6; v2 qualifier queries 100.0). Scope comparison fixed the v1 superset cases, not this score. |
| `COMPONENT_DESCRIPTIVE_QUALIFIERS` | "low voltage", "lv" | A [dated assumption](#assumption-low-voltage-is-descriptive-dated-28-october-2026). |
| Embedding text | — | `idea_embedding_text` sorts the vehicle list. This is a measurement-validity fix, not a model change. |

`scripts/score_edge.py` now also:

- reads `Probe_Type` and `Polarity` as well as `Case_Type`
- reports three outcomes: correct, wrong, and never retrieved
- lists unlabelled Potential Duplicate calls with their text, component, cosine and fuzzy score
- replays the component threshold with `--sweep-component LO HI`
- analyses a query that the submit form would refuse as a draft, and marks it

Each setting can be turned off with `PUT /api/v1/ai/settings`, or with `--disable` in the scripts.

## Assumption: "low-voltage" is descriptive (dated 28 October 2026)

`COMPONENT_DESCRIPTIVE_QUALIFIERS` in `classifier.py` lists "low voltage" and "LV". `component_key` drops them from component names before matching, as it already dropped a parenthetical such as "(LV)". Before this, no named list existed: "(LV)" was dropped only because it was in parentheses. So this adds a small list and the line that applies it. "High-voltage battery tray" is still a different component from "Battery tray".

- **Why:** this corpus has one battery tray, the low-voltage one, so "low-voltage" describes the part rather than distinguishing it.
- **Shelf life:** as high-voltage batteries enter the fleet, "low-voltage battery tray" and "high-voltage battery tray" become different parts. "Low-voltage" then becomes distinguishing, and this decision must be reversed by removing the two entries.
- **The underlying problem is entity resolution.** Whether a qualifier names a different part depends on what parts exist, which only a parts master can answer, not a string rule. Until there is one, a pair whose components differ only by an uncertain qualifier belongs in **Insufficient Evidence / Manual Review Required**, not in either confident verdict.

## Component matching: a wrong premise, and a guard that fixed nothing

- **The premise was wrong.** It was expected that component matching used `token_set_ratio`, so a qualifier name such as "Front spring bracket rear" would score 100 against "Front spring bracket" and clear any threshold. Component matching actually uses `fuzz.ratio` at 90 or above, on names normalised by abbreviation expansion and by dropping parenthetical and descriptive qualifiers. `token_sort_ratio` is used only by the (now off) symmetric lexical score.
- **The three qualifier names already fail.** They score 88.9, 85.7 and 86.4 on `fuzz.ratio`, so they never matched as the same component:

| Query | Query component | Candidate component | `fuzz.ratio` (used) | `token_sort_ratio` | `token_set_ratio` |
| --- | --- | --- | --- | --- | --- |
| FQ-001 | Cab mounting damper | Cab mounting bracket | 76.9 | 61.5 | 77.4 |
| FQ-002 | Front spring shackle | Front spring bracket | 85.0 | 60.0 | 85.0 |
| FQ-003 | Door check bracket | Door hinge bracket | 83.3 | 66.7 | 83.3 |
| FQ-004 | Front spring bracket rear | Front spring bracket | 88.9 | 88.9 | 100.0 |
| FQ-005 | Door hinge bracket lower | Door hinge bracket | 85.7 | 85.7 | 100.0 |
| FQ-006 | Exhaust heat shield front | Exhaust heat shield | 86.4 | 86.4 | 100.0 |
| v1 EQ-001 (positive) | Cab mount brkt | Cab mounting bracket | 91.9 | 91.9 | 91.9 |

- **The qualifier cases failed elsewhere.** They were flagged by the lexical rule, which didn't consult the component at all. `lexical_requires_component` is what fixed them.
- **The subset guard fixed nothing on any current set.** Not on the v2 hard set, edge v1 or edge v2, before or after `lexical_requires_component`. That holds before and after the determinism fix. It is kept for one case it does catch: names with positional qualifiers on both sides. "LH tail lamp lens" against "RH tail lamp lens" scores 94.1 on `fuzz.ratio` and would match at 90 without it. It would also matter if the threshold were lowered: without it, FQ-004's name matches at 88 or below.

### Component threshold sweep, 80 to 95

`score_edge.py --sweep-component 80 95` replays `classify_pair` on every labelled pair at each integer threshold. It reuses the retrieval results, which don't depend on the verdict. It was run with `lexical_requires_component` off and the guard off, then on. It was re-run on deterministic embeddings with the same results.

- **Verdicts:** the only flip on either edge set is v1 EQ-001 ("Cab mount brkt", 91.9). It's correct from 80 to 91 and falls to Insufficient Evidence from 92 up. No edge v2 verdict moved at any threshold.
- **Component matches without the guard:** they start at 88 or below (FQ-004), 86 (FQ-006), 85 (FQ-005, FQ-002) and 83 (FQ-003).
- **Component matches with the guard:** the three qualifier names never match.

With `lexical_requires_component` on, those component matches now decide verdicts. Lowering the threshold to 85 would turn FQ-002 back into a failure. FQ-005 and FQ-006 would fail too if the guard were also off.

**The margin is thin on both sides.** The one positive that needs fuzzy matching is 1.9 points above 90, and the closest negative name is 1.1 below it. On this evidence the threshold is only bounded to 89–91, and that rests on one positive pair. 90 was not chosen on evidence.

## Product limitation: the submit form refuses sparse text

The app refuses to submit a description under 20 characters. Two sparse_negative queries, "Al bracket." (11 characters) and "PC instead of PMMA." (19), couldn't be submitted, so they were analysed as drafts, which the scorer marks. **This matters most for sparse_description, the case the system handles best:** both v1 sparse duplicates are found, through the semantic route. A user writing as tersely as the v2 sparse queries can't reach analysis at all.

## Limitations

- **Two or three pairs per probe type.** Each result is about a mechanism, not a rate.
- **The set was written knowing the rules**, so it tests over-firing, not generalisation. `lexical_requires_component` was written after seeing these failures, so this set no longer tests it fairly either.
- **The component-routing fix depends on retrieval it doesn't control.** The five pairs it fixed (FQ-002 to FQ-006) are shown at ranks 10 to 15 in a top-15 window, and that window is still selected lexically (exact, then fuzzy, then cosine). Two of them (FQ-002, FQ-004) occupy the last shown slot. One more candidate with a higher fuzzy score would push them out of view. They would still count as correct, since they aren't duplicates, but they would no longer be surfaced. The fix's measured effect on these cases depends on that retrieval.
- **rank@1 is measured against partial labels.** The corpus contains true duplicates that aren't labelled: for Q-0005, SYN-015 is the same low-voltage battery tray proposal as the labelled H-0005, and it ranks first. rank@1 therefore understates ranking quality rather than showing a ranking defect.
- **No LLM rerank.** Ollama wasn't reachable.
- **Database state.** The edge ideas are loaded and rolled back in one transaction. The database had 111 historical ideas before and after every run, and no VAVE-FH or VAVE-EH codes.
